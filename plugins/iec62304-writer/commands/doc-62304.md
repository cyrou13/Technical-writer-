## OUTPUT LANGUAGE — STRICT

All artifacts written by this command (every file under `docs/`, item
frontmatter values such as `title`/`description`, body content,
`[TODO]`/`[GAP-...]` markers, and aggregated reports) MUST be written
in **English**, regardless of the user's conversational language or
any global `CLAUDE.md` instruction. Conversational replies to the user
MAY follow the user's language; written outputs are English-only. This
applies to every sub-agent and skill invoked from this command.

Run the complete IEC 62304 class A documentation pipeline. Output is
local Markdown under `docs/`; nothing is pushed anywhere.

## The contract every agent works under

Items separate **normative** sections (exported: present-tense
behaviour, design or assessment) from **internal** ones (`## Notes`,
`## Open questions`, `## History` — never exported). Every SRS has a
`kind` and declares its constants in `parameters:` (one name, one value
across the store); acceptance criteria are numbered; third-party
components are identified in `docs/ots.yaml` only; the cybersecurity
architecture lives in four views of `docs/dt-clinical-context.md`. No
competitor names, no code or test paths in SRS text, no dates or
markers outside internal sections. Details: skills `items-store`,
`submission-readiness`.

## Steps

1. **Map** — run `code-archeologist`. Blocking.

2. **SRS first** — `requirements-writer` → `docs/items/SRS/` (kinds,
   parameters, numbered criteria). Blocking, so the following agents
   have the SRS IDs and parameter names.

3. **In parallel** (one message, several Agent calls):
   - `architecture-writer` → `docs/items/SDS/`, `docs/ots.yaml`, the six
     narrative sections of `docs/dt-clinical-context.md`
     (`links.implements`).
   - `test-evidence-collector` → `docs/items/TC/` (`links.verifies`,
     existing `test_id` only).

4. **Safety risk analysis** — `risk-analyst` → `docs/items/RSK/`,
   `docs/items/PRSK/`; may create `kind: safety` mitigation SRS and add
   `links.mitigates` on existing items (History line only). Blocking.

5. **Cyber risk analysis** — `security-analyst` → `docs/items/THR/`, the
   four security views; may create `kind: security` mitigation SRS / TC,
   add `links.mitigates`, fill `links.triggers`. Blocking.

5bis. **Production risk analysis** — `production-risk-analyst` scans
   the production artefacts (Dockerfile, CI workflows, package scripts,
   deploy / helm) → `docs/items/PRSK/`; may create production
   mitigation SRS / SDS / TC and fill `links.triggers` towards RSK or
   THR. No production artefact → "Production phase not applicable", go
   to step 6. Recommended for class IIb (AAMI TIR57, IEC 81001-5-1
   §6.1). Blocking.

6. **Usability analysis (IEC 62366-1)** — `usability-analyst` →
   `docs/items/USC/`, `docs/items/URSK/`, `SRS-VIEWER-*`, E2E TC. No UI
   surface → "62366-1 not applicable", go to step 6bis. Blocking.

6bis. **Coverage of the mitigation SRS (pass 2)** — steps 4–6 created
   mitigation SRS (`SRS-MIT-*`, `SRS-CYB-*`, `SRS-PROD-*`, `SRS-USE-*`)
   that did not exist at step 3, so no SDS implements them and no TC
   verifies them. **Re-run `architecture-writer` AND
   `test-evidence-collector` in parallel** (one message, several Agent
   calls). Both are idempotent: they read the existing SRS, scan the
   modules / tests that cover them, and only create the missing SDS /
   TC or add `links.implements` / `links.verifies` (one History line)
   on existing items. When no module or test exists yet for a
   mitigation SRS, the writer leaves the SRS to `_to_implement.md` (a
   TC with `test_id: "[TODO]"` is never coverage). No mitigation SRS
   created → skip. Blocking.

7. **Build** — `python tools/build_docs.py`. Check
   `docs/generated/{10_SRS,20_SDS,30_STD,40_traceability,50_risk_analysis,60_cyber_risk_analysis,70_usability_analysis,_to_implement}.md`
   and `coverage.json` exist.

8. **Review** — `compliance-reviewer` → `docs/generated/99_compliance_review.md`,
   release-gate offenders first.

9. **Export suggestion** — when `dt-config.yaml` exists and at least
   one MAP item was entered, end the summary with: "for the QMS-ready
   deliverables, run `/doc-build --release` (or `/doc-srs-export
   --release`)". When `dt-config.yaml` or MAP are missing, list them as
   prerequisites of the release export (informational, never blocking
   for `/doc-62304`).

10. **Summary to the user** (16 lines or fewer):
   - coverage metrics from `coverage.json` (existing tests only; planned
     TC separately),
   - SRS count per `kind`, and the kinds left empty,
   - RSK / PRSK / THR / URSK open, and those with a non-acceptable
     residual (alert if > 0),
   - OTS components registered, fields left `[TODO]`,
   - the six `dt-clinical-context.md` sections filled / empty,
   - items in `_to_implement.md`,
   - release-gate offender count per rule — what stops `/doc-build
     --release` today,
   - paths of the main outputs.

## Guard rails

- `_codemap.md` not produced at step 1 → stop and ask.
- Build failure → show the Python error, do not hide it.
- Never commit or push unless asked.
- Optional `$ARGUMENTS`: if non-empty, pass it as the scope to the
  agents (e.g. `/doc-62304 packages/auth`).
